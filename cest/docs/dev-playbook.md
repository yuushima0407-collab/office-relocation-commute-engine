# 開発プレイブック（島田ゆうき）

自分が開発で守る原則をまとめたもの。CEST（オフィス移転の意思決定支援）の開発で得た
学びを、ドメインに依存しない形で抽出した。

**使い方**
- 新規開発時、AI（Claude等）に文脈として渡し、品質基準と進め方を毎回そろえる。
- 「自分の開発の型」を確立する。
- 例の括弧内は CEST 由来の具体例。原則自体は他のドメインに転用できる。

## 0. 最上位の心がけ

- **完成時に「すべての設計判断を理由つきで説明できる」状態で作る。**
- そのために、**実装・課題解決のアプローチは常に複数の選択肢を出してから選ぶ。**
  「なぜそれを選び、何を捨てたか」が残る開発にする（AIに作らせる時も、まず選択肢を出させる）。

---

## 1. 設計の原則

- **本質の課題から始める。** ユーザーの「表面の要望」でなく「本当の困りごと」を先に言語化する。
  （例：最短通勤の算出 → 本質は「関係者を納得させ説明責任を果たせる決定」）
- **機械は選択肢を絞るまで。価値判断は人に残す。** 重み付けで1位を押し付けず、トレードオフを見せて選ばせる。
  「最適」を決めるには価値判断（交換レート）が要り、それを勝手に決めると恣意的で信頼を失う。
- **非線形・文脈依存な価値は1スコアに潰さない。** 分布や「誰が影響を受けるか」を見せ、人の判断にかける。
- **同じデータを目的別に使い分ける。** 安定が要る判定には外れ値に強い指標、足切りには最悪値、のように。
- **足すだけでなく削る判断をする。** 意思決定に寄与しない機能は、作れても削る。
- **危険・不能・推定は消さず明示する。** 候補から削除せず警告・フラグで伝え、判断材料を残す。
  ユーザーを行き止まりにしない（結果ゼロでも原因と次の一手を出す）。

## 2. アーキテクチャの型

- **層を分ける。** Web/入口層は薄く（受付・検証のみ）、ロジックは素のデータで動く純粋関数に。
  → フレームワーク無しでテスト・再利用できる。
- **入力は宣言的に検証する。** 型・範囲・必須・列挙をスキーマで定義し自動チェック。余計な項目は弾く。
- **出力は契約として固定する。** 出力形をスキーマ化し、テストで実出力と照合してドリフトを防ぐ。
- **後方互換を保つ。** 旧バージョンの入力を壊さない（使わない受け口も残す）。
- **重い計算の前に軽いフィルタ。** 生データで落とせる条件を先に、計算が要る条件を後に置く。
- **デプロイは用途で選ぶ。** 散発的アクセスなら固定費ゼロのサーバーレス等、トレードオフで判断。

## 3. テストの型

- **例ベースより性質ベースを重視する。**
  - 決定論：同じ入力 → 必ず同じ出力。
  - 単調性：条件を強める/緩めると結果が一方向に動く（逆転はあり得ない）。
  - 頑健性：想定外の入力でも落ちず、黙殺せず警告する（落ちる・サイレントバグの両方を防ぐ）。
  - 後方互換：旧入力でも正しく動く。
  - 契約：出力がスキーマ通り。
- **仕様ごとのゴールをテストに落とす。** 各段階の「できたと言える条件」をテストにして、テストで確認しながら進める。
- **境界値を狙い撃つ。** ちょうど閾値・空・超過・欠損(None) など壊れやすい際を意図的にテスト。
- **純粋関数にしておけば、手作りデータで速くテストできる。**
- **足りないテストは正直に記録する。**（未テスト領域をメモに残す）

## 4. 開発の進め方

- **キックオフで「誰の・どんな課題・どう解決するか」を確定する。**
  AIと議論して決め、**確定したことを md に記録**する（以後の唯一の拠り所＝SSoT）。
- **まず「細い糸を1本通す」。** 入力→出力が端から端まで動く最小プロトタイプを先に作る。
  機能を盛り込むのは後。動く骨格ができてから枝（機能）を足す。
- **仕様を段階に切り分けて進める。** 仕様ごとにゴールを明示し、それをテストに反映して、段階的に積む。
- **流れ：** 本質課題 → 仮説 → 最小実装（細い糸）→ 性質テスト → 穴を探す → 直す → 限界を正直に記録。
- **検証の種類を分ける。** 設計判断は分析で検証、製品仮説は実ユーザーで検証（次の一手として明示）。
- **PR は適切な粒度で。** 1 PR = 1つの論理変更。機能ごとが既定値。大きければ分割し、
  **リファクタは機能と別PRに分ける**（混ぜると何を直したか曖昧になる）。
- **ブランチ → PR → テスト緑 → マージ。** 「push した」と「main に入った」は別物。実際に main を確認する。
- **協働は"境界"を決めて引き継ぐ。** 専門が違う相手には、①形の契約（出力スキーマ）②意味と表示の仕様
  ③相手の分野の言葉への翻訳、の3点で渡す。**形の契約（スキーマ）だけでは相手は実装できない**——
  各フィールドが「何を意味し、どう表示するか」を別途定義して初めて、相手はこちらのコードを読まずに作れる。

## 5. AI活用の作法

- **下書き・実装はAIに任せてよい。判断・検証・デバッグは自分がループに残る。**
- **アプローチは必ず選択肢を出させてから選ぶ。** 決めたことは md に残す（0章・キックオフと対応）。
- **AIに渡す知識は"索引＋必要時ロード"で軽く保つ。** 全部を常に読ませると文脈が膨らみ注意が散る。
  索引（場面→該当章）を常時持たせ、詳細はその時必要な章だけ読ませる。
- **AIが書いたものも「何を・なぜ・どう」説明できて初めて自分のもの。**
- **「ローカルで動く」は本番互換の保証ではない。** 依存は宣言ファイルを一次情報源に、ビルドは本番に近い環境で。
- **盛らない。** やってないことを言わない。未検証は「仮説」と言う。分担は正直に。

## 6. 外部記憶・セッション運用（AI協働を軽く保つ）

長い対話は文脈が膨らんで重く・不正確になる。状態を md に外部化し、各セッションを軽く始める。

- **「現在地」ファイルを1つ持つ。**（例 `docs/state.md`）
  目標／完了・進行中・次の一手／確定した決定／未解決の問い／関連 doc へのリンク。これが再開の入口。
- **セッションの区切りで現在地を更新 → 新セッションは「現在地＋必要な doc だけ」読んで再開する。**
  重い会話履歴を引き継がない。**会話＝揮発、md＝永続。**
- **常時持たせるのは小さく：** standing rules ＋ 索引 ＋ 現在地ファイルだけ。
  詳細（playbook 各章・各仕様）は必要な時にロードする。
- **決定・選択の結果は会話に埋もれさせず md へ移す**（キックオフ §4 と対応）。
- 重くなったら要約（`/compact` 等）するか、現在地を書いて新セッションに切り替える。

### セッション引き継ぎの手順（「引き継ぎして」と言われたら AI が実行する）

1. `docs/state.md` を開く（無ければ作る）。
2. 次の項目を、いまの会話の内容で最新化して書き直す：
   - **目標**：このプロジェクトで達成したいこと
   - **完了**：done のこと
   - **進行中**：いま取り組んでいる所（どこまで進んだか）
   - **次の一手**：次セッションで最初に着手すること
   - **確定した決定**：理由つきで（後で蒸し返さないため）
   - **未解決の問い**：保留中の論点
   - **関連 doc**：playbook・仕様・スキーマ等へのリンク
3. 保存し、「新セッションは `docs/state.md` ＋ 必要な doc だけ読んで再開してください」と一言添える。

> 新セッションを始めるときは、まず `docs/state.md` を読み、そこから必要な doc だけ辿る。
